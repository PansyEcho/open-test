# Design

The user requested both the existing Codex entry and direct OpenTest HTTP entry. An ephemeral CLI approximates the agent entry while allowing reproducible event timing; it does not measure desktop UI rendering. Both agent arms use gpt-5.6-sol/xhigh, the same Chinese request patterns and the existing configured provider. No low-effort arm runs.

The atomic arm receives the same prepared operation semantics and invokes three atomic tools. This deliberately gives the baseline the benefit of prepared knowledge as well; the original discovery-heavy task is historical reference only. The fast arm passes the request to one MCP tool: a single Jev decision selects among closed intent/action/target/reason options, then deterministic code queries the real ticket, checks a unique cancellable refund, cancels it and independently reads back its identity and REFUND_CANCEL state. Jev receives only the masked request, candidate labels, shared business contract and closed questions. The model never invents a refund number, API name, state rule or business result.

The isolated experimental HTTP service on loopback port 8789 executes the fast workflow and reuses existing OpenTest business endpoints on 8788. Both the aggregate MCP tool and direct HTTP arm call that same route. Prepared job files restrict the experiment to its exact authorized requests; this is a feasibility harness, not a newly installed production plugin or page.

Contract and QA environment checks remain present and are timed when performed during execution. Preparation checks availability; every existing operation execution validates its current catalog and environment binding, so the experimental workflow does not repeat four extra metadata HTTP reads for every request. Only verified current operation definitions are used. Business identity translation stays local; prepared expected refund IDs never select runtime targets. Unknown cancellation outcomes use the existing query/execution records and readback instead of a new write request.

Existing cancellable QA samples were exhausted during developmental probes. The fixed-version prepare_refund_entry_v1 dynamically queries registered booking, refund and change interfaces, accepts a real ticketed non-SAPL adult passenger with supported source-verified enums, rejects any noncancelled refund or any change history, then creates and independently reads back a new PENDING_APPLY refund. Each measurement uses a distinct refund; underlying bookings may be reused only after prior refunds are cancelled. No database state is edited. Preparation occurs before each timed request and is reported separately, making this a running-service feasibility experiment rather than a cold-start guarantee.

Measure five independent requests per path as a feasibility pilot, reporting median, range and count completed within ten seconds; do not infer a reliable P95 from five observations. Rotate order and use distinct refund orders for writes. Measure the direct invocation of the same fast workflow separately from agent invocation so that the remaining outer-model cost is visible. Data preparation and service startup are disclosed separately. Errors remain in success and ten-second denominators; no automatic model retry or fallback hides failures.

The experiment will recommend the smallest entry change supported by actual measurements. A fast inner tool is not sufficient evidence that the existing desktop chat meets ten seconds.

## Verified pilot outcome

All fifteen distinct new refunds were cancelled and independently verified. Atomic Codex, one-tool Codex and direct HTTP medians were 39.678s, 30.948s and 7.109s; ten-second completion counts were 0/5, 0/5 and 5/5. These targets reused one underlying booking/ticket, so the result establishes this workflow's feasibility rather than broad order coverage. Across both Jev entry paths, nine of ten inner workflows finished within ten seconds; one took 12.510s due to a slow real query. No ten-second SLA or reliable P95 is claimed.

The recommended next integration is direct OpenTest routing to the fixed Jev workflow. An aggregate MCP tool still leaves a median 22.398s outside the service workflow. Preparation took 912.181s separately. The evidence, developmental failures, token usage and reproduction commands are under `.opentest/jev-refund-entry-final/`; earlier smoke evidence remains unchanged. Thirty-six focused tests, five additional negative model probes and three live HTTP rejection checks passed. OCR delegation's four accepted Medium findings were fixed and verified. Task-owned services on 8788 and 8789 were stopped and both ports checked free.

# 接口语义分类与上游触发 Case 设计

日期：2026-10-24。状态：设计方案，尚未实施、未执行 QA 造数或补单。

本方案针对 `RefundFacade#billSupplement` 生成失败，并满足“自动分析接口用途和读写属性、查询或创建上游数据、通过真实上游入口验证目标”的要求。通用实现不包含 refund、supplement、业务包名或具体表名特例；下文业务名称仅用于验收样本。

实施时沿用活动 OpenSpec change `share-code-baselines-and-publish-cases`，先补充 proposal、相关 delta specs、design 和未完成 tasks，再修改程序。本设计不将任何实施或验证任务标为完成。

## 1. 已核实的现状

1. 原任务 `task-fb319ea734a9fbb8` 固定扫描 `scan-20261020062539-c796af848b-6894bbf5`，目标的 `mutability=UNKNOWN`、`executable=false`，原始原因是“Facade操作的读写属性尚未确定”。不是业务接口返回失败。
2. `DsfSourceDiscoverer._mutability` 使用方法名和 action 动词判断；`billSupplement` 未命中。相同机制也不能保证名称以 query/get 开头的方法没有业务写入。
3. 当前共享基准流程的 `_generate_knowledge` 调用 `SharedInterfaceKnowledgeService.generate_interface`，后者将扫描零版契约保存为个人草稿，没有调用 AI 分析实现。`operation_summary` 初始来自方法和 DTO 注释。界面上的“生成接口知识”不能证明进行了语义分析。
4. 当前契约补充支持用途、请求和响应说明，没有承接读写分类的字段；执行目录仍消费扫描里的分类。只改提示词或知识正文不会改变执行判定。
5. UNKNOWN 在本系统 Facade 目录、统一执行校验及另一个 DSF 执行入口中被拦截，但外部 DSF 已允许按潜在写操作执行。相同业务接口从不同目录进入可能得到不同结论。
6. V4 在 DATA 后隐式直接调用 `generation.operation_id`，响应断言也默认读取这个直接响应，没有独立的上游触发入口。
7. 已有数据函数具备查询、无数据时创建、重新查询、身份/状态验证和有限状态调整能力；这部分应复用。当前退款系统按“补单”检索未找到已发布共享数据函数，仓库中的样例不能当作可执行资产。

业务源码核查范围：退款使用上述任务的固定扫描，补单系统使用基准 `baseline-af9f2755501d4b5ba8c1b1ee6b32fa4a`、commit `c9f52e57682c3233657f2820f964966b0e49a6da`。这些源码事实不代表两个版本已在 QA 兼容部署。

## 2. 导入后由 AI 分析接口语义

流程为：程序扫描固定源码与依赖 → 保存接口身份、路由、DTO、调用关系及零版契约 → AI 分析每个接口用途和副作用 → 校验证据 → 保存同一接口的契约草稿。沿用当前逐接口进度和续跑机制，不创建另一套任务平台。

程序负责发现真实接口及结构，AI 负责解释业务语义。解析器遗漏接口、依赖、类型或路由时仍修复解析器，不通过 AI 猜出不存在的接口补齐扫描。

### 2.1 最小分析产物

在既有接口契约 JSON 中扩展语义信息，沿用契约修订和个人草稿/共享发布，不新增独立分类表：

| 内容 | 用途 |
| --- | --- |
| 接口用途 | 描述实际业务动作，供检索和 Case 规划使用 |
| `mutability` | 沿用 READ_ONLY / WRITE / UNKNOWN |
| 副作用说明 | 说明涉及的业务状态、数据写入、业务事件、远程动作及触发条件 |
| 源码证据 | 复用固定扫描的文件、符号、行号引用，支持对应实现和调用链 |
| 未解决调用或条件 | 表达不能确认的下游、反射、动态分派等，不以模型自报置信度替代证据 |

不新增宽泛的接口类型体系。查询、创建、触发、回调等业务角色可体现在用途与具体 Case 步骤中；路由协议继续由程序确定。

### 2.2 分类规则

- WRITE：任一可达分支会改变业务数据/状态、发出业务消息、触发异步业务、调用有业务副作用的远程接口，即为 WRITE；“先查询后写入”同样是 WRITE。
- READ_ONLY：已分析实现及必要下游契约，足以确认不改变业务状态。不能仅凭名称、注释、HTTP 动词、某次调用没有写入或空结果，就认为只读。
- UNKNOWN：必要调用无法解释或证据不完整。保留原因，不强迫 AI 二选一。已存在确切业务写入证据时，即使其他分支不完整，也足以判为 WRITE。
- 普通诊断日志、指标不因此把所有查询归为 WRITE；业务审计、业务锁、缓存更新等则分析其业务影响和查询重放条件，无法确认时不批准为观察函数。
- AI 读取实现、必要的 Repository/Client 封装、状态机与事件消费者、固定依赖契约。无需为每个接口生成整份实现长文，也不要求无边界展开所有系统。
- 服务端检查引用身份、固定版本、已读范围、符号及已知调用关系；有明确写证据的候选不能提交 READ_ONLY。程序验证证据边界，不声称能完全证明 AI 的所有语义判断。

`billSupplement` 应根据创建退票单并推进状态的实际实现判为 WRITE。`saveReport`、`batchRetry` 等也应按实现分析，不靠增加几个动词修补。

### 2.3 分类必须进入实际执行链

个人草稿、共享接口详情、Case 编译、Runtime 函数目录、统一执行服务和数据函数/Oracle 必须使用本次固定契约修订的同一分类。不能出现页面已显示 WRITE，而执行层仍读取旧扫描 UNKNOWN 的情况。

扫描原始事实不改写；语义分析追加既有契约版本。已有契约补充不能硬写 revision=1 覆盖，复用现有递增修订及 CAS。分类改变参与契约兼容判断，READ_ONLY 改为 WRITE/UNKNOWN 时，依赖它的查询和 Oracle 要重新验证，不能继续当作只读。旧任务不静默跟随 latest；需要补充语义时，通过同任务明确修订冻结依赖后重编译，不改写历史执行记录。

历史按名称推断的 READ_ONLY 不能自动升级成“AI 已分析”。新建/修订的观察步骤应补做实际使用接口的语义分析，或选取已有、经过约束的只读数据库查询。补分类失败不抹去已完成扫描，也不阻塞无关接口成果；显示该接口分析失败或证据不足。

## 3. 读写分类与执行资格分开

现行规范 `codex-system-operations` 明确把 UNKNOWN 与不完整绑定一起禁止执行，因此这是既有产品规则和多层代码共同造成的行为。原意可理解为防止潜在写入被当作查询，但将其扩大为所有操作禁用，与本项目已授权的线下测试需求不符。

新规则如下，实施时同步修改现行规则对应的 delta spec：

| 使用位置 | READ_ONLY | WRITE | UNKNOWN |
| --- | --- | --- | --- |
| 已授权 QA/UAT 目标或触发动作 | 允许 | 允许 | 按潜在写动作允许，保留未知说明 |
| DATA 中明确创建/调整步骤 | 允许 | 允许 | 按潜在写动作允许，必须回查 |
| 数据查询、验证、只读 Oracle、轮询 | 允许 | 不允许 | 不能充当只读观察；先补分析或换可靠只读方式 |
| 未解析路由、缺少必要执行契约、环境错误、超出任务范围 | 均阻塞，与分类无关 | 均阻塞 | 均阻塞 |

UNKNOWN 不是“无须校验”，也不是“自动改成 WRITE”。仍执行固定身份、参数类型、环境、任务授权、请求去重等既有约束，不增加逐步审批。`generate_only` 始终不执行业务。

查验所有仍在使用的入口，统一 Facade 与 EXTERNAL_DSF 规则；不用第二套门禁。生成前提前检查真实执行前提，错误显示准确接口、阶段和原因，不能再次吞成笼统的 not executable。

## 4. Case 保留验证目标，独立选择触发入口

在现有 Case 模板中增加可选的触发计划，旧模板缺省为直接调用：

| 项目 | 设计 |
| --- | --- |
| 验证目标 | 沿用 Case 所属系统、接口和基准，本例是 billSupplement |
| 触发模式 | direct 或 upstream，使用明确枚举 |
| 触发操作 | 一个精确、已登记且固定版本的入口，带实际请求映射 |
| 可达依据 | 上游入口到目标的路径、分支条件及固定源码引用 |
| 目标验证 | 明确本场景必须到达目标；来源是实际调用观察及业务结果 |

复用 data_functions、data_calls、oracles、source_scopes、knowledge_dependencies 和执行记录。不建立通用工作流引擎，不允许任意脚本或无限 DAG。

### 4.1 自动寻找上游

1. 从目标接口精确身份反查入边；区分真实入口可达、配置声明、MQ 关系及版本差异。
2. AI 读取调用方实现、转换器和前置分支，选择能够到达目标且影响范围最小的可执行入口。内部 Java 方法只用于解释，不能自动变成远程可执行接口。
3. 每次只引入本场景必要的操作、源码和契约；发现关系不自动导入整个上游系统。
4. 目标缺数据时分别发现数据提供操作；“调用目标的人”不必等于“生产目标所需数据的人”。需求满足即停止扩展；发现循环或没有进展时报告具体缺口。
5. 跨系统使用同一明确 QA/UAT 环境，固定各方源码和契约，按现有规则选择调用方 Profile。展示出来的版本差异不能自动视为可兼容执行。

直接模式适用于目标返回值、业务分支及目标自身幂等；上游模式用于正常补单闭环。若上游会拦截某个输入，不能为了覆盖目标异常分支修改上游预期，应另建 direct 场景。上游“已有退票单所以跳过”的场景属于上游跳过逻辑，不能报成 billSupplement 已执行。

### 4.2 执行顺序和响应归属

准备数据并回查 → 执行前观察 → 调用一个触发入口 → 等待异步结果并取得目标调用证据 → 执行后断言。

- direct：入口就是目标，维持原行为。
- upstream：只调用上游入口，执行器不再隐式补调 billSupplement。DataFunction 不得暗中调用同一目标。
- 保存真实触发操作及其响应，单独保存观察到的目标调用；内部 RPC 没有 OpenTest execution_id 时引用实际日志/调用观察，不编造一条目标 Operation 执行回执。
- `trigger_response` 与 `target_response` 分开。上游的“受理成功”不能绑定为 billSupplement.success；拿不到下游真实响应时，不允许写依赖该响应的断言。
- 若创建业务任务会自动触发目标，这个创建操作本身就是 TRIGGER；把不会触发目标的前置工作放在 DATA，提前开始观察，不能创建后再额外触发。

界面继续在 billSupplement 下展示这些 Case，清楚标注“直接调用”或“从 supplement 触发”。执行详情分别显示数据复用/创建及回查、触发受理、目标调用观察、最终业务断言；未拿到目标证据时不能把整条链路画成成功。接口列表展示用途、读写分类和分析状态，详情能展开依据与未知原因。

## 5. 上游查询与造数闭环

查询和造数都属于验收范围，不能以“找到一笔现成数据”代替创建能力。复用现有共享函数模型，形成固定版本的业务数据方法；每次运行动态取数据，不保存试跑单号为默认数据。

### 5.1 两种准备目的

| 方法目的 | 查询/创建的对象 | 输出与完成标准 |
| --- | --- | --- |
| 准备 billSupplement 直接调用输入 | 真实原订单/票号、账单、符合条件的 REPORT 及请求所需业务关系 | 回查后的 reportId、账单字段、关联键；不执行补单目标 |
| 准备上游补单触发条件 | 上述业务前置数据，加正确类型的补单 process/task、原始账单和 REPORT 关联 | 回查后的 reportId、对应任务身份、可触发状态和精确触发条件 |

两者按实际步骤复用现有数据函数，不因为名称相近就强行做一个含大量布尔开关的函数。目标模式需要不同的准备完成条件。

### 5.2 查询路径

- 用户给定票号、主体或订单时保持原对象；未给定时自行发现适合本场景的数据源和候选，不要求用户提供 capability ID。
- 查询原交易/票号、ARC/BSP 账单、REPORT、对应 process/task 和退款侧状态；身份、币种/金额关系、业务类型、关联关系及分支状态以固定源码为依据。
- 正常新补单候选必须排除已经落单或已有退票单等上游跳过条件。负向场景则按自己的前置条件查询，不能一律筛选为正常数据。
- 候选匹配覆盖完整前置条件。查询得到若干不合格记录，不等于“已有可用数据”；在有界查询范围内继续筛选，无适用记录时进入创建。
- 网络错误、契约字段缺失、响应解析失败不是“无数据”，不能因此造数。

现有 `match_source` 主要检查结果是否为空；应复用 `filter` 等步骤将满足条件的候选交给匹配判断，不能先取第一条再把所有验证失败解释成无数据。用户指定的对象状态不符时保留原对象与失败原因，不能另造对象替换。初始查询应能从有界列表或已登记只读数据源取得真实业务身份，避免“先要票号才能查到票号”的循环依赖；分页、日期范围等查询控制参数与业务身份分别核验，不伪造业务 ID。

### 5.3 创建路径

优先调用实际业务提供方的准备/导入/创建接口。根据场景建立真实关联的原单、账单、REPORT 和正确类型任务；已有符合条件的原单可以复用，不要求每次重建整套订单链。

已核实 `ReportFacade#saveReport` 只保存 REPORT 及扩展信息，不创建补单任务；返回成功也可能只是返回同票号、PNR、交易类型的旧记录。因此它只能作为部分准备步骤，不能单独构成上游造数完成。

实施时继续发现具体 process 创建/导入能力；若现有业务 API 不足，则使用已登记 QA 数据库能力，按固定 Mapper/表定义与业务规则准备必要前置记录。SQL 仍受现有参数化、单语句和作用域约束，不另建数据库访问层。未掌握真实关联、必填字段或状态约束时报告该创建路径不可用，不编造标识。

禁止直接写退款成功结果、修改断言预期或将已成功记录重置成待处理来伪造正常补单。允许的状态调整只针对本次已验证身份的前置测试数据，且必须有业务依据。

若所用任务在创建后立即被定时器/MQ 消费，应使用业务已有的暂存/激活方式；若不存在，则将会自动触发的创建步骤安排为 TRIGGER，并调整观察顺序。不能随意发明一个业务不支持的暂停状态。

### 5.4 创建后回查与复用

- 创建响应不是完成依据：重新读取账单、REPORT、任务及关联对象，核验身份、关联、类型和真实状态，再返回动态输出。
- 原任务/数据执行回执用于处理超时和中断；写结果未知时先回查，不因换了 request_id 就再造一套。
- 使用已有数据库约束或业务唯一键应对同时创建；冲突后查回实际记录并验证，不新增分布式锁，不覆盖不相关记录。
- 复用数据的方案与新建数据的方案均真实试跑，通过后才能按现有规则发布共享函数。函数发布与 Case 发布保持既有边界，不因 Case 成功自动公开个人草稿。
- 不要求测试后撤销业务结果；只按既有要求处理本次临时数据，不改动他人的共享测试记录。

## 6. 异步观察与结果判定

当前 CaseOracle 执行一次观察，没有通用的有界等待语义。已确认 batchRetry → 异步事件 → MQ → 消费者这一真实链路，因此需要在既有观察器上增加有限等待，而非重试写操作。

观察声明明确：只读函数、成功条件、已知失败终态、最大总时长与采样间隔，均有执行上限。未达终态继续只读观察，出现明确失败停止等待，超时报告尚未验证完成。网络/契约错误保留独立诊断；等待期间不重新触发目标。只读采样不会发起消费 MQ 消息来观察业务。

采样次数还要计入现有单 Case 调用预算，并响应任务取消；不能只限制每个 Oracle，却让多个观察器的总执行时间无界。复用现有任务与执行阶段保存已知结果，恢复时先读取回执和业务状态，再继续剩余观察。

每次新采样必须读取新状态。当前 `_call_operation` 会根据阶段和参数生成去重键；若轮询重复使用同一键，会一直命中第一次结果。因此采样序号进入既有请求身份，同一采样重放去重，不同采样实际查询。复用已有执行记录，不新增轮询服务或队列。

成功需要同时满足：准备条件通过、本次触发已发生、目标调用达到本场景要求、实际业务断言通过。接口返回 success、MQ ACK、OpenTest 自己调用上游的日志或已有最终状态，均不能单独证明内部目标被调用。

使用已有可查询的实际调用日志/服务记录与 reportId、process/taskId、票号、时间范围建立关联。补单流程会改写 traceId，不能假设一个 traceId 贯穿所有跳；若无法唯一关联本次目标调用，报告观察缺口，不能宣称目标覆盖完成。

不承诺系统内部 RPC 恰好执行一次：已有 MQ 可能重投。平台保证相同具体触发请求不盲目重发，同时回查是否产生重复业务结果；幂等场景单独显式执行，不混入正常准备。

覆盖增强仍采集退款目标系统及正确部署版本，不能改成采集触发系统。当前成功证据检查要求 TARGET Operation 等于 Case 目标，必须理解新的触发/目标区别；覆盖计数不能证明某个 Case 的内部调用，也不替代业务断言。等待结束前不能提前结束测量窗口。

## 7. 已发现的具体坑点及处理

| 已有证据或限制 | 风险 | 方案中的处理 |
| --- | --- | --- |
| 知识生成目前不调用 AI，执行目录也不读语义补充 | 仅补 prompt 或文字无效 | 接入逐接口分析，贯通契约修订与所有消费者 |
| 扫描、目录、执行、Runtime 函数各有分类判断 | 同一操作从不同路径行为不同 | 统一分类来源和阶段规则，覆盖 Facade/外部 DSF |
| saveReport 可能直接返回旧 REPORT；没有创建 process/task | 造数“成功”但触发没有工作对象 | 查回完整对象关系，不仅检查 success/reportId |
| batchRetry 查询 REPORT 后按 ext.fromTask 分流 | 名称相似但进入另一条业务链 | 当前基准中 fromTask=true 进入 UnifiedIssueSupplementScenario，不能当作退款任务；退款路径需核对旧 process、业务类型和处理节点 |
| batchTaskRetry 重置新任务表，空 IDs/无更新也可 success | 选错接口或什么都没发生 | 不能当作必然到达退款目标的触发入口 |
| batchRetry 要求未录入/待确认状态和有界日期，按筛选条件批量滚动 | 任意日期或宽筛选可能处理无关数据 | 用实际数据日期及精确条件；核对实际查询实现和命中对象，不把 pageSize 当写入范围限制。无法约束时换已证明可限定对象的入口或报告缺口 |
| 上游已有单/已录入会提前返回 | Case 通过但目标未执行 | 场景化前置条件、执行前状态与真实目标调用观察 |
| 异步受理、MQ 消费成功不代表补单成功 | 提前通过或提前回查误失败 | 有界只读等待，分别记录触发、处理和业务结果 |
| 锁冲突、调度器竞争、MQ 重投 | 并发取走数据、重复处理 | 优先独立测试对象，触发前复核条件；不追加盲目写重试，不删除业务锁 |
| traceId 被上游及目标重新生成 | 只用 traceId 无法关联结果 | 组合实际业务键、调用记录和执行时间；无法证明则保留缺口 |
| 回查使用与首查相同幂等键 | 永远读取写前结果 | query/requery/poll 使用已有阶段身份加采样序号 |
| 重扫、接口知识发布、JAR 和 DSF 版本不同 | 读取了一个版本却调用另一个版本 | 固定各方契约/扫描，核验路由及部署；不自动跟随 latest |
| 新增触发依赖只存到模板、未进入单 Case 依赖列表 | 发布/跨机器执行时丢上游来源 | 将触发、准备、观察实际依赖全部纳入已有固定引用、发布兼容性及可见性检查 |

仍需在实施中实测的两项，不在此宣称已经打通：可精确限制本次退款补单对象的上游触发接口；可构造完整退款 process/账单/REPORT 关系的创建路径。已确认的 batchRetry 和 saveReport 不能直接替代这两项验证。

## 8. 实施顺序与验收

1. **语义与执行规则**：接入扫描后 AI 用途/读写分析及带证据契约；修复 UNKNOWN 的阶段规则与明确诊断。验证 billSupplement、无副作用查询、名称像查询但实际写入、发消息接口、证据不足接口；分类必须在页面、编译与执行一致。
2. **数据闭环**：完成补单输入和上游触发前置数据的查询/创建/回查；分别实测已有数据、无数据创建、误匹配、创建返回旧记录、超时未知结果和状态不满足。缺少 process/task 时不得报准备完成。
3. **上游触发执行**：反向发现精确调用链、独立触发计划、参数与响应归属、有界观察和本次目标调用证据；正常场景只提交一次触发，执行器不补调目标。上游跳过、MQ 受理无结果及观测缺失不得报目标测试成功。
4. **现有产品链路衔接**：验证接口/Case 个人草稿与共享发布、依赖兼容性、旧 direct Case、跨机器与环境执行、覆盖增强和结果页；前端若变化，更新资源版本并通过运行中的 HTTP 服务验收。
5. **独立验收收尾**：采用 billSupplement 的 ARC/BSP 合适场景和另一个系统的真实接口做通用性回归；遵守注释、日志上下文及参数规则，完成 OCR delegation 独立审查、受影响验证和严格 OpenSpec 校验。仅实施、真实闭环和必要验证全部通过后更新对应任务；change 仍有其他未完任务时不归档。停止本次启动的服务并检查 8788，保留用户已有服务。

完成标准包括两条真实数据路径：一条复用现有合格数据，一条创建必要上游前置数据；都要实际触发并回查。不以 mock、模板生成、成功受理或目标结果被直接写入来代替业务验收。

## 9. 改动范围与机制必要性

| 扩展 | 独立需求 / 实际消费者 | 具体失败模型与决策 |
| --- | --- | --- |
| 既有契约增加 AI 分类与副作用证据 | 用户要求导入后分析；查询/Oracle 与动作执行消费 | 名称误判导致禁用或把写操作用于观察；分类决定可用阶段 |
| 模板增加触发计划 | 用户要求从上游验证目标；编译器和执行器消费 | 原模型强制直接调目标或重复调用；计划决定唯一触发入口 |
| Oracle 增加有界等待与逐次采样身份 | 已证实异步事件/MQ；结果判定消费 | 受理后未完成、观察读到缓存旧结果；新采样决定完成/失败/超时 |

其余复用既有接口关系、固定源码、版本化数据函数、执行去重与记录、契约发布及覆盖流程。不新建表、全系统扫描任务、通用编排框架、锁服务、调度平台、额外签名或快照体系。

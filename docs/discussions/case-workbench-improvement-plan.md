# Case 同名与任务体验改造方案

日期：2026-10-30。状态：本轮功能、数据库分组分页和真实 MySQL 查询采样已完成；两轮 OCR delegation 审查及用户指定的 DeepSeek Harness Flash Max 代码审查/修复复核已结束。实施进度以活动 change 的 tasks.md 第 26 节为准，不代表整个 change 已完成。适用项目：OpenTest。

本方案覆盖 Case 同名、查询慢、起止时间、执行总览、覆盖增强耗时、长任务进度及本轮确认的相关缺陷。沿用活动 change `share-code-baselines-and-publish-cases`；采用的行为已纳入 proposal、design、delta specs 与 tasks，未完成项继续保留，不能把本文的目标当作已通过验收。

核心决定：保留现有 Case 身份与发布体系，区分真正新增、原 Case 修订、参数变体和覆盖复测副本；查询从全量正文改为有界摘要；执行逐条保存结果，页面显示真实阶段。界面只增加一行摘要、必要时间与可展开原因，不新增复杂工作台。

## 1 已确认问题与证据边界

| 问题 | 已确认事实 | 尚不能下的结论 |
| --- | --- | --- |
| Case 同名 | 独立生成分配新 Case ID；旧独立成果继续有效；参数标签、单项修订已存在；列表缺批次时间 | 不能仅凭同名判断内容重复，也没有发现跨基准混读证据 |
| 覆盖副本混入新增 | 基础 Case 被复制为增强种子，清空绑定后分配新 ID；新增统计又只比较新旧 ID | 这是可成立的代码路径，尚未逐条核实用户当前所有同名记录来自哪条路径 |
| 查询开销 | 改造前存在全量正文和逐条重读；现已完成三个核心查询各 100 次的前后对照，结果见 §3.1 | 当前样本不能代表多人并发容量，也不能据此推断整轮覆盖增强中模型或业务执行的占比 |
| 进度假停滞 | 一次 GET 失败会停止覆盖轮询；回到前台未恢复当前共享覆盖页；结果整批结束后保存 | 页面不刷新不能直接证明后台已停止 |
| 状态误导 | 断言不符合预期为 PARTIAL + BEHAVIOR_DIFF，页面显示部分完成；复测读取异常返回 None | 不能把所有 PARTIAL 均改成失败，也不能把未知结果改成零 |
| 时间不准确 | 覆盖复测会重写任务开始时间；非运行状态同步会重写 ended_at；等待状态也可有 ended_at | Generation 创建、Case 登记、发布、任务开始与执行开始不是同一个时间 |
| 覆盖耗时 | 首次增强执行所选生成批次的完整冻结集合；保存补充草稿同步调用复核 Agent | 正常程序流程是基线执行一次、补充后增强集合复测一次，不是模型后固定复测两轮 |

已有一次补充 Agent 运行记录为 1437.98 秒，约 23 分 58 秒。该数是整个 Agent 运行耗时，包含分析、工具调用与等待，不等于纯模型推理时间，也不是整轮增强耗时。

- `opentest/application/coverage_assistance.py`：`_bind_owner`、`_verification_execution`、`_visible_selection`、`_added_cases`（原逐条读取的 `_find_visible_case` 已移除）。

## 2 Case 同名的处理规则

### 2.1 身份和展示分开

Case 标题是业务描述，不是唯一身份。不改为“所有名字必须唯一”，也不通过自动加随机后缀掩盖来源。

| 情况 | 身份规则 | 页面呈现 |
| --- | --- | --- |
| 同模板、参数不同 | 保留不同 variant 与 Case | 延续已有参数差异标签，例如“订单查询 · 已支付”与“订单查询 · 已取消” |
| 顶部重新生成 | 成功后替换当前接口本人草稿，失败保留原草稿 | 生成期间旧草稿继续可用；历史生成和执行记录保留 |
| 编辑原 Case | 复用已有 revisions 接口，case_id 不变 | 显示修订时间与版本；发布后只更新该条当前指针 |
| 网络重发同一请求 | 复用原 request_id 和已有回执 | 返回原任务或执行，不能再次生成或再次写业务 |
| 覆盖原样复测副本 | 保留增强执行所需的独立 ID，固定来源 | 标记“基础复测”，不算业务新增；作为关联复测项呈现 |
| 覆盖中调整基础场景 | 新增强 Case，不改写原共享 Case | 标记“基于原 Case 调整”，明确两者独立 |
| 覆盖真正补充场景 | 新 Case | 标记“覆盖新增” |

2026-10-30 按用户确认调整：顶部“生成 Case”重新生成所选接口全部本人草稿，完整成功后替换，失败保留旧草稿；不新增“新增场景”按钮。原 Case 的“编辑”继续走单项修订。未完成任务使用“继续任务”，失败增强使用“重试本轮”，已完成增强使用“开始新一轮”。不增加重复确认弹窗。

### 2.2 先解释，再减少重复行

主列表保留业务名称和已有参数展开，仅补一行次要信息，例如：

`订单查询 · 已支付`

`10-30 14:20 生成 · 基础生成`

不同批次同名仍分别可找到。用户可用一个批次筛选器查看某次生成；批次内部时间相同时，详情显示现有 generation_id 的短尾号，不新建批次编号体系。

有服务端可验证来源、且运行内容未变化的覆盖副本，归入来源 Case 的“覆盖复测记录”展开项，避免默认主列表重复铺满。展开后仍能查看并选择精确副本；批次筛选下必须可以看到该批次所有成员。归组依据是当前可见的稳定 case_id，原 Case 修订不强制拆散分组；副本仍标明所用旧版本，归组不赋予旧版本读取权。若来源已不可见或不能安全归组，副本独立展示“基础复测”，不能隐去它，也不能泄漏来源的私有标题或内容。调整过的场景与真正新增场景始终独立展示。

列表返回“业务 Case 行数”和“关联复测项数”时分别命名；执行总数仍来自实际选择，不从折叠后的可见行数推算。折叠是界面行为，不删除数据库记录，不改变发布或执行资格。

服务端按业务行分组后分页，返回关联复测数量，组内明细另行分页；参数变体同样不能因跨页丢掉组成员或变化参数摘要。当前页来源可见性批量核验，不能逐行读取原 Case 正文，也不能由前端拼接多个页面碰运气成组。

### 2.3 修正覆盖新增统计

当前种子复制与新 ID 差集组合，会把基础副本也算新增。最小调整是复用 `seeded_case_selection`，在种子创建时由程序保存模板到来源 `CaseSelection(case_id, generation_id, variant_id)` 的精确关联，编译后带入绑定。

来源引用仅用于区分复测、调整和新增，并定位可见原 Case；真实消费者是新增计数、列表归组与增强结果展示。放入现有 handoff/Generation JSON，不另建来源表、哈希或全库相似度系统。

服务端维护来源，不能相信模型自报的来源，也不能依据标题或 `coverage-base-` 前缀推断。在编译/发布时对固定来源做一次直接比较，覆盖目标调用、参数、步骤、断言、数据函数及其固定依赖等执行相关字段；标题、展示 ID 和时间不作为业务差异。将来源三键与复测/调整/新增/未知分类保存到 binding 的可选字段，列表和轮询不重复比较 DSL。

种子模板的内部身份保持稳定，改业务标题不改变来源；受控修改原种子保留来源并标为调整；额外场景使用新的模板身份。模型提交的全量草稿若删除、重命名、拆分或合并种子，服务端必须核验原冻结复测集合是否仍被完整表示；不能只凭新名字判新增。来源映射不能由模型自由覆盖；无法确定映射时显示未知并阻止以“完整基础复测”宣称覆盖结果，要求在现有草稿修订中补正。不同参数的扩展 Variant 必须明确区分原冻结参数与额外场景，不把同模板新增参数全部当复测。

例：8 条基础复测 + 2 条新增，显示“复测 10 条，其中新增 2 条”；不能显示“新增 10 条”。若其中 1 条基础场景被调整，则显示“基础复测 7、调整 1、新增 2”，复测总数仍为 10。

复测继续遵守增强 Generation 的精确绑定。不得为了去重直接把原 case_id 填进增强 Generation，导致旧共享内容被替换或破坏当前可见性校验。

### 2.4 历史记录与请求重试

旧记录没有来源时显示“历史来源未记录”，不能批量按标题合并，也不能继续将所有新 ID 标成新增。新增数量显示“已确认新增 N、来源待确认 M”；N=0 且 M>0 表示尚不能确认新增数，不声称没有新增。旧的 seeded_case_selection 与 coverage-base-N 只作为调查候选，前缀不能证明后续模型修改后的真实来源。只有固定版本的完整运行内容、精确种子选择和一一对应关系均可验证时，才给出“与基础内容一致”的只读诊断；不能由此猜测调整项来源。该诊断按需执行，不放进每次列表或轮询。历史生成时间缺失显示“未记录”；数据库迁移登记时间不能冒充生成时间。持久补齐或清理历史需另列准确范围，不默认执行。

当前共享页基础生成仍沿用 startCaseGeneration → getOrCreateCaseRequestId，会话存储中的 requestIdentity 已含基准、接口、环境、视图和执行模式；不能把这条活跃调用链误认为退休旧页面。共享修订、执行和覆盖重试目前只保存在内存。复用既有会话存储方法，补齐员工隔离，并为修订/执行/覆盖重试统一员工、系统、基准、环境、视图、动作及规范化精确选择的键；只排序语义上无序的选择集，不改变实际执行顺序。

响应未知时保留请求身份，先查询已登记任务或执行；明确成功回执确认后可清除“未确认”标记，后续用户主动执行是新请求。不能简单把所有 4xx 都当成可清除重发，例如认证过期或身份冲突应先恢复访问、查询原回执；只有业务明确拒绝且确认未创建/派发时，才允许修正输入后创建新请求。参数变化必须形成新的请求，不能将旧请求 ID 用于不同内容。不新建幂等表，也不自动重放未知结果的写请求。

## 3 查询性能方案

### 3.1 先建立真实基线

令 `P=/api/v2/systems/{system_id}/baselines/{baseline_id}`，优先测：

1. `GET P/cases?view=published|mine`。
2. `GET P/cases/{case_id}/executions?environment_id=qa|uat&view=...`。
3. `GET P/coverage?operation_id=...&environment_id=...&view=...`。

另记录“打开入口目录”和“查看一次执行记录”的浏览器完整耗时。使用现有 Server-Timing 与慢日志，记录样本量、p50、p95、最大值、错误率、响应字节、sql_count、连接/池等待/查询/解析耗时。响应头 app 不是完整页面耗时，parse 也不代表全部 CPU 工作，不能简单相减就认定瓶颈。

2026-10-30 实测补充：正常公司登录后，仅使用当前员工授权范围内的 GET；MySQL 8.4.10。原服务与当前代码各完成 100 轮三个查询，最终有效样本各 300 条，全部 HTTP 200 且响应字段验证通过。原页面读取全量正文，新页面读取当前入口摘要页/历史摘要/覆盖状态，数据粒度按实际页面用途改变，不能解释为相同完整正文接口的同比提速。

| 页面读取 | 原读法 p50 / p95 / 最大（秒） | 新读法 p50 / p95 / 最大（秒） | SQL 次数（原→新） | 响应字节中位数（原→新） |
| --- | --- | --- | --- | --- |
| Case 列表 | 0.737 / 1.733 / 4.599 | 0.486 / 0.696 / 1.097 | 3→9 | 2,920,608→29,113 |
| 单 Case 执行历史 | 1.202 / 2.092 / 5.924 | 0.156 / 0.188 / 0.367 | 9→6 | 113,372→604 |
| 覆盖状态刷新 | 6.398 / 10.099 / 25.240 | 0.137 / 0.192 / 0.211 | 38→5 | 16,142→1,056 |

执行历史这一行采用 DeepSeek 审查修复后另取的 100 个有效样本（全成功）：旧记录缺少逐项摘要时只批量补读当前页正文。已对真实旧执行核对摘要与详情均为 PASSED，起止时间因原记录未保存继续保持未知；修复前的 0.200 秒/5 SQL 不是最终结果。

Case 原读法返回当前基准 58 条本人 Case；新读法返回所选接口 38 条中的第一页 20 条，增加的 SQL 用于完整组计数、变化参数名及批次选项，参数/展示正文只取本页。完整覆盖报告另采样 10 次，p50 0.223 秒、p95/最大 0.246 秒、7 次 SQL，来源统计与固定结果保持一致；本轮批量读取修复前同一新版 full 请求曾为 5.927 秒、25 次 SQL。旧覆盖请求数据库耗时中位数 5.566 秒，说明重复数据库往返/载荷读取是本样本的重要瓶颈。

分页正确性另以真实数据核验：38 条本人接口 Case、57 条已发布接口 Case 跨组页/成员页完整找回，搜索 BSP/bsp、中文、百分号、下划线和批次筛选均符合授权全集。初次并行浏览两个本机端口导致登录 Cookie 干扰、产生 401 的采样已单列废弃，关闭页面轮询并稳定登录后重新完成上述 100 轮。以上是单工作台顺序热读诊断，未模拟 10 个独立工作台的 10 分钟并发负载，也不代表全量容量验收或真实业务重新执行。

选实际小、中、大数据规模，报告真实 Case、批次、历史条数；冷读与热读分开。重点热读分组采集至少 100 个成功样本，错误和超时另报；少量冷读明确样本限制。诊断只发目标 GET，不顺带改配置、生成 Case 或执行写业务。现有 benchmark 脚本包含服务启动与配置 PUT，不能原样称作只读诊断。

### 3.2 按热点做有界读取

| 路径 | 改造 |
| --- | --- |
| 入口目录计数 | 同一授权条件下 SQL 聚合 Case 数，附在接口摘要中；不再读取全量 Case 正文用于计数 |
| Case 列表 | SQL 先按员工视图、基准、接口过滤，再分页读取摘要；详情按精确 Case 读取 |
| 接口摘要 | 当前为了少量字段读取完整压缩契约；先测开销，若明显则 SQL 只提取所需字段或复用已有摘要，不预先新增冗余列 |
| 执行历史 | 一次核验当前 Case，按精确选择与环境过滤后分页，批量读取本页状态摘要；只打开详情时解压完整结果 |
| 覆盖轮询 | 轻量状态与完整报告分开；权限批量核验；同一请求中每份固定 Generation/Execution 只读取解析一次 |

默认页大小 20、上限 100，稳定排序追加唯一 ID。`view` 保持 published/mine 的权限含义，新增独立 `representation=summary|full`；不得用 view=summary 覆盖原权限视图。总数和列表采用相同过滤条件，不能对全量 ID 分页后才过滤权限，不能把本页条数当总数。

Case 摘要最低保留：case_id、generation_id、variant_id、template_id、operation_id、title、impact_status 及原因、blocked_reason、ordinal、parameter_values、公开/草稿修订、后端派生的 executable 及阻止原因、来源分类和时间。CaseVariantV4 没有 status，不能继续使用页面现有 variant.status === BLOCKED 的无效判断；编译阻塞读 blocked_reason，执行结果状态属于另一结果对象。参数只投影当前可见 Variant；不能为补分组摘要带出私有兄弟 Case。分页分组返回组内授权成员数和变化参数名称，不要求加载全部成员正文。详情继续按精确 ID 读取；执行前仍由后端重新核验资格，摘要不能替代授权判断。

优先使用既有 `summary_json`，其已包含 selected_cases。执行历史先在 SQL 内匹配 case_id/generation_id/variant_id 及环境，再 LIMIT，批量读取本页摘要；新执行补必要的逐 Case 状态摘要。旧记录选择字段缺失时保留现行拒绝/旧记录核验规则，仅在当前游标的有界候选窗口检查正文；页可能不足时显式返回 has_more/next_cursor，不能把不足页当末页。旧记录无法低成本准确计数时 matched_total 为未知，不补零，也不扫描全部历史凑总数。当前精确请求的通过率分母来自回执，与历史分页总数是两回事。

先减少查询次数与传输量。仅在实测执行计划证明需要时增加索引；本期不默认扩大连接池、加分布式缓存或新查询框架。状态轮询可以批量读必要身份，但不能为验权限而重新下载完整报告或运行内容。

### 3.3 验收

沿用现行规范：10 个独立工作台、独立缓存的冷读与 10 分钟混合负载，普通读取 p95≤3 秒、样本最大≤5 秒、health≤500 毫秒，错误和缺字段不算通过。若环境未达到则列出实测值和未通过项，不承诺无依据的提速百分比。

固定 20 条首屏时，Case 或历史总数增长不能造成逐条 SQL 线性增长；入口计数不得读取 Generation 正文；轻量进度不得读取源码、完整契约、完整执行结果或完整覆盖报告。同一普通请求不持有业务写锁。

## 4 起止时间和进度

### 4.1 时间口径

| 对象 | 开始 | 结束 | 等待/排队 |
| --- | --- | --- | --- |
| 生成任务 | 第一次实际进入执行 | 本次任务真实终态首次确定 | 等待客户端/补充信息不展示为完成；创建时间可用于排队说明 |
| 覆盖增强轮次 | 本轮首次实际开始 | 本轮完成、失败或中断的时间 | 基线、补充、复测分别记录阶段耗时，复测不重置整轮开始 |
| 一次执行请求 | 所含执行中最早实际开始 | 全部执行终结后的最晚结束 | 未启动显示等待，不把 created_at 当实际开始 |
| 单条 Case 执行 | 准备该 Case 数据前 | 该 Case 结果及既有收尾完成 | 未执行结束时间为“—” |

生成与覆盖优先复用 TaskRecord 时间；对 WAITING 状态的既有 ended_at 只作为旧状态段记录，不作为整个任务完成。保留首次开始；状态同步、页面刷新和重复回执不推进已确定的结束。执行对象及逐 Case 结果缺少真实起止时，在既有 JSON 增加可选时间字段，旧数据不推测补值。

网页生成启动目前已在 web_generation.py 的派发前写 started_at；需要核对并统一为首次实际 worker 执行时刻，且保留恢复同一 run 的原始开始。原生接手在其已授权的真实执行入口补写首次开始，打开链接或准备 handoff 不算启动。_sync_case_task 和 WebGenerationService._settle 均遵守首次真实终态结束时间规则；覆盖 _bind_owner 不重置整轮开始。不能简单声称生成任务完全没有 started_at，也不能仅因字段存在就假定所有入口语义正确。

区分“产物生成时间”和“生成并验证任务结束时间”。Case 可先产出而验证仍在运行，不因已有 Generation 就显示全部完成。耗时使用后端时间差，统一保存 UTC，页面按当前时区展示。

### 4.2 展示真实阶段，不展示模型内部思考

页面只放当前步骤、已耗时、最后活动和最近 3 条可展开记录。例如：

`执行中 · 正在准备第 3/10 条 Case 的数据 · 已耗时 2分18秒`

`14:20:10 已完成接口与参数检查`

`14:20:28 第 1 条通过`

`14:21:03 第 2 条断言未通过，继续执行下一条`

生成阶段：读取接口 → 准备数据/构建场景 → 校验草稿 → 保存产物 → 按任务模式验证。覆盖阶段：基线执行 → 采集分析 → 补充场景 → 增强集合复测 → 分析收尾。

已知执行集合显示完成数/总数；模型生成尚不知道场景总数时只显示阶段和耗时，不把整任务 0/1 展成细进度或制造百分比。

复用 TaskProgress 和 Runner 的公开事件回调、增量事件游标。摘要事件只包含已发生的工具/业务阶段与安全结果，不输出完整提示词、模型内部推理、业务请求正文或凭据。

心跳与业务事件分开：执行进程仍在线可以定期上报存活，但不能每隔几秒编造“又完成一步”。页面区分“最后业务活动”和“最后连接成功”；没有新活动时说明仍在等待响应。优先复用已有进程活性证据；若现有记录不能提供运行中存活，才在既有任务记录增加独立心跳时间，不以普通 GET 更新时间冒充。

修复 `save_business_record` 重建粗进度覆盖细进度的问题。进度写入使用既有锁读取最新任务再合并，不能让持旧 TaskRecord 的 reporter 覆盖草稿或新状态。Runner 的运行中事件使用既有唯一写入路径，不让多个工具同时调用仅适用于 worker 结束后的 append_public_event。

### 4.3 刷新与恢复

可见且任务运行时，上一请求结束后约 3 秒查询一次。失败保留上次内容，标注同步失败与最后成功时间，继续有限退避的只读查询；隐藏时暂停，重新可见立即读取当前共享入口。系统、基准、环境或接口切换后丢弃旧响应，保持一个轮询器。

状态请求读取轻量进度；阶段变化、完成或用户展开时才读取完整报告。网络中断或后台恢复仅恢复观察，不重发执行、生成、reset 或业务写入。暂不新增取消按钮；将来如做取消需区分停止后续步骤与已提交业务不可撤销，不在本期夹带实现。

## 5 执行记录和简洁界面

### 5.1 复用本次执行请求

一次勾选执行已有 request_id 回执，保存精确 CaseSelection 与 execution_ids，可跨多个 Generation。以此作为“本次执行”关联，不新建批次表。新增读取投影按本人、当前基准、环境和精确选择核验，不直接开放整份 Generation 结果。

新读取入口建议为 `GET P/case-execution-requests/{request_id}`，返回本次允许查看的结果摘要与分页明细。实际路径在 delta spec 中定稿。只有单条旧执行记录、没有可靠请求回执时，按旧执行展示，不按时间相近猜测合批。

本次请求中若部分 Case 后来被替代或失去可见性，明确“部分记录当前不可见”，仅显示授权明细，不显示完整批次通过率，也不静默缩小分母后冒充完整结果。若全部选择均被修订替代，则展示“所选 Case 已修订，旧执行明细当前不可查看”，不显示空白成功页或 0%。一个请求可以跨多个 Case 和 Generation，单条修订只使该条旧执行失效，不必然让整个请求不可见；单条请求或所有成员均变化时才会全部不可见。历史内容权限保持现行边界，本期不新增“执行发起人可读任意已替代旧内容”的例外。

覆盖面板也必须区分“本人当前接口没有增强记录”和“本人已有增强，但固定 Case 已变更导致旧详情当前不可查看”。现有 interface_projection 把两者都返回 coverage=None，需要在确认工作流属于当前员工/基准/环境后，返回不含旧详情的明确不可用原因。存在性提示只针对本人已归属工作流，不暴露他人的任务；不回退展示旧报告，不伪装尚未执行。

### 5.2 统一结果口径

读投影给出稳定 outcome，持久化原始 status/failure_kind 保留兼容。逐项区分通过、断言未通过、执行错误、数据/环境阻塞、等待、运行中、未知。PARTIAL + BEHAVIOR_DIFF 显示“断言未通过”，生成部分可用和覆盖部分完成继续保留原有含义；不能用通用 PARTIAL 统一判失败。

已完成时，整体通过率定义为“通过条数 / 本次计划执行条数”；失败、阻塞、未完成均不能算通过。运行中以“已完成 3/10 · 通过 2 · 未通过 1”为主，不展示容易误读的 100% 动态通过率。总数为零或数据无法完整读取时显示“—”。已完成计数表示有确定终结结果，遇到明确阻塞也算已收尾，但原因单列，不能声称验证了业务失败。

展示层沿用现有 caseResultState 的失败分类，后端摘要与详情使用同一映射规则；清理异常、观察失败不得混成通过。摘要计数覆盖当前授权请求全集，不只统计当前页。

### 5.3 逐条结果保存

执行器在每条 Case 完成后把类型化结果交给外层保存；先持久化结果再推进完成数。详情存既有执行 JSON，摘要存现有 summary_json。阶段与心跳更新只写轻量事实，不每 3 秒重新压缩全部结果。

异常收尾读取最新执行记录，保留已经完成的结果，不能从初始空 running 对象覆盖。结果未知的在途业务标明需核实，不能自动重放。进度与终态写入使用既有事务和所有权约束，防止迟到回调把完成状态退回运行中。

这些是待补的写入规则，不能假定当前 save_execution 已具备：在现有行锁内读取最新状态，核验有效执行者；逐项以 variant_id 合并已完成事实，收尾与恢复也使用相同合并路径；终态执行不接受迟到业务回调重写状态或覆盖已完成结果。只读统计补齐可更新派生展示字段，不能改业务结论。完成数量在同一 execution/阶段内单调不减；阶段切换可以归零下一阶段计数，不能用全任务单调规则把基线完成数带入复测。失败恢复保留已完成结果与未知业务说明。

保留原页面导航，仅用一行总览和表格。以下均为示意数据：

## 6 覆盖增强提速

分阶段记录排队、基线 Case 执行、材料获取/解包、覆盖分析、补充 Agent、只读复核、增强 Case 复测与收尾。每一阶段使用真实进入/退出时间；复用已有模型 elapsed、reset/dump 等事实，但不能用 reset 到 dump 代表纯业务执行时间。

先实施与实际问题对应的改动：

1. 让进度查询轻量化，避免任务最慢时不断重组完整报告并重复查询。
2. 将草稿保存与耗时只读复核解耦。核心草稿成功后及时返回，覆盖响应给出 coverage_review 的状态、对应 handoff/revision 和已有 run_id。没有待复核 IGNORE 时为 not_required；其余为 pending、running、ready、unavailable 或 stale。复核只针对覆盖缺口忽略建议，仍是辅助能力，不新增 Case 发布审批；失败/超时不回滚草稿、不阻断原本可发布的有效 Case。
3. 在现有工作流 model_runs 内登记唯一 REVIEW 与绑定 revision。派发由本次已授权草稿请求在短事务提交后触发：将既有 AgentRunner.run 中的独立 worker 启动与阻塞观察拆开，新增内部非阻塞启动入口；原 run 保留组合启动+观察的兼容行为。启动只进行有界的本地校验与创建进程，不等待模型结果；不新建线程池、队列或另一套 Agent 框架。持久唯一 run_id 与既有工作流/工作台所有权负责去重，不复用父生成任务已持有的付费排他门禁，避免父任务等待复核而复核又等待父任务。
4. 维护回调只做有界 read_state、超时状态检查与已完成结果收尾，不能启动新付费运行，也不能阻塞调用 run/attach。已有存活 run 继续观察，worker 已终态才读取最终 evidence；登记后启动结果不明时先核实本地运行证据，不自动派发第二次。保留全局 SUPPLEMENT_RUNNING 等业务阶段，复核状态是子状态，不替换主阶段以免破坏 _save_dispositions 准入条件。调用方通过已有 read_context 观察；pending 不能伪装 ready。IGNORE 在收到本 revision 的复核或明确 unavailable 后，由生成模型提交有理由的 final 决定，沿用现有“允许不同意复核”的规则。
5. 复核返回前核对 handoff revision 和阶段：不匹配的结论仅记录 run 完成情况，不能改写新版 gap.decision。若子代已发布、工作流进入复测，维护仍收尾已登记 run，但仅保存运行状态/成本，不回写已发布决策或重开增强。当前 revision 无可用复核时明确 unavailable/stale，让生成模型按现有规则最终判断。一次独立复核不因草稿修订或观察恢复而重新派发。
6. 当前 RuntimeToolSettings 与 Runner 都没有可直接复用的复核截止预算。为这个已确认会阻塞用户的可选只读步骤，新增一个 coverage_review_timeout_seconds 设置，初始建议 180 秒，允许显式调整；这是一项产品等待上限，不是性能实测结论。截止时间从登记待复核开始，同时写入已有 model_runs 和 reviewer worker 请求；启动失败或到期仍未启动也明确 unavailable，不无限 pending。worker 自己执行运行中的超时终止，避免服务重启后预算丢失。到期显示 REVIEW_TIMEOUT/复核不可用，利用既有取消与状态机制核实原 reviewer 退出，不终止生成 Agent、不重放业务、不再开第二次复核。截止时旧 revision 的迟到结论不生效。
7. 对测量中发现的重复材料读取、重复解析或无即时消费者的报告构建做局部优化。复用材料仍必须核验部署二进制与冻结源码匹配，不能只凭 commit 认为可复用。

条件性优化只在计时证明收益后执行。保留现行完整冻结选集和必要的基线/复测两次测量，不擅自改为只跑新增 Case。可能相互影响的写业务默认串行，不能简单并发来提速。Agent 阶段不承诺固定几分钟完成；即使外部工具慢，也必须看到当前阶段、最后真实活动与已完成结果。

## 7 相关缺陷的具体处理

| 缺陷 | 修复及验收 |
| --- | --- |
| 一次读取失败停止轮询、后台回来不恢复 | 当前共享页统一调度；模拟一次 GET 失败、隐藏再显示，均恢复读取且不重复写业务 |
| 断言失败标部分完成 | 按 status + failure_kind + 已存断言归类；失败行、总览、覆盖结果一致 |
| 复测读取异常当作未复测 | 无 verification ID 才是尚未复测；有 ID 的读取失败显示不可用，保留旧画面，不返回假零 |
| Case 修订后覆盖投影变成假空 | 本人已有工作流但固定选集已变化时显示“旧结果当前不可查看”；不能显示“没有增强记录”，也不开放旧报告 |
| 编译阻塞 Case 仍显示可执行 | 以 blocked_reason 与后端派生 executable 驱动按钮及说明，移除不存在的 variant.status 判断；后端继续强制核验 |
| 复测重置整轮开始、同步重写结束 | 首次开始/真实终态时间稳定；阶段耗时独立；等待不冒充完成 |
| 覆盖基础副本算业务新增 | 程序固定来源；8 基础 + 2 新场景显示新增 2、复测 10 |
| 页面刷新丢未确认请求身份 | 复用会话存储，未知结果先查回执；与原 request_id 绑定，不重新写业务 |
| 异常收尾可能覆盖已完成 Case 结果 | 从最新执行事实收尾，故障前的已完成结果仍可见，未完成保持未知 |

其余未复现、无充分证据的问题单独报告，不趁本轮扩大为扫描器、权限体系、数据清理或整体架构重构。

## 8 数据与接口的最小变更

| 载体 | 复用/新增 | 约束 |
| --- | --- | --- |
| Case/Generation/Handoff | 复用现有 ID、版本、种子选择；补可验证的来源关联 | 现有 JSON 可选字段；来源由服务端控制，旧数据允许未知 |
| Case 摘要 | 参数标签、生成时间、来源类型、可见关联与修订信息 | 批量关联时间；不暴露其他人的任务正文或同批草稿 |
| TaskProgress | 复用阶段、数量、事件游标；按需补真实存活时间 | 合并最新记录，未知总量无百分比 |
| 执行 JSON / summary_json | 增加真实起止、逐项 outcome 摘要、计数 | 每条完成持久化；既有索引、归属、请求身份不变 |
| 执行请求回执 | 复用 request_id 与精确选择 | 本人读取；部分不可见时不显示完整批次率 |
| 覆盖工作流 | 阶段时间、草稿复核 revision 与状态 | 当前 revision 校验；重启沿现有阶段恢复，不重复未知业务 |
| 既有 RuntimeToolSettings / reviewer worker | 可选复核超时设置与持久截止时间；Runner 内部分离启动/观察 | 仅限辅助只读复核；维护不阻塞、不启动新付费运行，不增加通用任务框架 |

默认不新增表、索引或迁移。若实现前验证表明历史分页无法用现有 JSON/索引有界完成，需先给出执行计划及最小字段/索引变更，再同步 change，不能把新基础设施作为默认前提。

## 9 实施顺序与验收

| 阶段 | 工作 | 可交付结果 |
| --- | --- | --- |
| A | 更新选定 change；三个 GET 的基线测量；修轮询、标签、读取异常 | 不再假停滞或误报成功；有真实性能基线 |
| B | 来源规则、批次/时间摘要、原样副本归组、稳定请求身份 | 能解释同名；新增统计正确；生成和修订入口清楚 |
| C | 逐条结果保存、统一 outcome、执行请求总览与真实起止 | 一条完成即可看到；中断保留结果；通过率分母准确 |
| D | 轻量进度与增量事件；列表/历史分页与批量读取；复核异步化 | 长任务持续可观察，普通页面查询不被完整报告拖累 |
| E | 根据分阶段耗时做覆盖局部优化；真实 HTTP 页面与多工作台验收 | 说明实际收益和未解决的外部耗时，不用假进度代替优化 |

时间展示从 B 开始即可交付；C、D 对运行事实的写入补齐后，运行中展示才算完整。先做单工作台定位，不以长时间压测阻塞确定的小 Bug 修复。开发工作量在性能基线及来源规则验证后估算，不现在承诺整体覆盖耗时缩短比例。

最少验收场景：

- 同名不同参数、两次独立生成、单项修订、覆盖副本同时存在，用户能区分且均不误删。
- 8 条基础 + 2 条新增，新增数为 2；调整原场景不算原样复测；标题变化不改变身份。
- 修改或删除种子模板、改名、拆分后来源判定明确，无法确认时不虚报新增。
